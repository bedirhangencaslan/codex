This audit covers the FastAPI backend, the SQLite schema/seed path, and the React frontend. Line references are to files under `sepet/` unless otherwise stated.

## 5. Risks: the ten most serious

1. **Order-detail IDOR exposes customer PII.** `GET /api/orders/{order_id}` has no auth dependency and returns address, phone, and note (`main.py:119-139`). Any client can enumerate IDs and read customer data. Concrete fix: require `get_current_user`, return the order only when `order.customer_id == user.id`, or add explicit role-based access for the linked restaurant/courier. The frontend currently relies on this endpoint (`web/src/pages/OrderPage.tsx:14-18`), so it must also pass auth context/API access.
2. **Status literals are mojibake, blocking core order flow.** Order creation and the schema default write `hazÄ±rlanÄ±yor` (`main.py:199`, `schema.sql:60`), while courier assignment requires `hazırlanıyor` (`panels.py:174`). Customer confirmation writes mojibake `onaylandÄ±` (`panels.py:237-239`), while review eligibility requires `onaylandı` (`reviews.py:32-36`), as does the restaurant-detail review check (`main.py:107-111`). Earnings use the correct Unicode literal (`panels.py:257-263`). Concrete fix: define one Python `Literal`/enum status set, use it in all queries and inserts, migrate existing rows to normalized values, and add a schema constraint.
3. **Tokens never expire and logout does not invalidate them.** `auth_token` stores only token, user ID, and creation time (`schema.sql:21-25`); creation has no expiry (`accounts.py:50-56`); token lookup has no age check (`auth.py:10-15`); frontend logout only removes localStorage (`web/src/AuthContext.tsx:56-59`). Concrete fix: add `expires_at`, reject expired tokens, delete the token on logout, and rotate tokens after password/login changes.
4. **SQLite foreign keys are effectively disabled.** Connections are opened without enabling enforcement (`db.py:11-14`). This lets writes violate declared relationships (`schema.sql:10`, `schema.sql:23`, `schema.sql:29-30`, `schema.sql:36-37`, `schema.sql:45-46`, `schema.sql:55-63`, `schema.sql:70-72`). Concrete fix: execute `PRAGMA foreign_keys = ON` immediately after `sqlite3.connect` in `get_db()`.
5. **Money uses binary floats and client-shaped input.** Price, fee, minimum, balance, total, and unit price are `REAL` (`schema.sql:5-7`, `schema.sql:18`, `schema.sql:49`, `schema.sql:59`, `schema.sql:74`), and order calculation uses float multiplication/sums (`main.py:166`, `main.py:174-175`). This invites rounding drift. Concrete fix: store integer kuruş (or SQLite NUMERIC consistently), perform integer arithmetic, and validate quantity with a sane upper bound. Pydantic currently only enforces `quantity > 0` (`main.py:20-22`).
6. **Rating calculations are inconsistent.** The list endpoint treats the whole review average as one additional rating equal to the seed rating (`main.py:49-61`), while detail passes every individual review row into `displayed_rating` (`main.py:103`), which always counts the seed rating once (`reviews.py:13-15`). Consequently, the same restaurant can display two different ratings. Concrete fix: compute both views through one SQL expression or one shared aggregation function that defines whether the seed score is included.
7. **Reviewer emails are exposed publicly.** Restaurant reviews return `u.email AS user_email` (`main.py:94-99`), the frontend displays it (`web/src/pages/RestaurantDetail.tsx:92-96`), and review creation echoes it (`reviews.py:50`). Concrete fix: return a masked display name or explicit public username, and do not leak user email through public restaurant responses.
8. **Registration, order, courier, and menu inputs are under-bounded.** Registration accepts long/malicious restaurant names, cuisines, and emoji (`accounts.py:14-23`); order address/phone/note have no backend length validation (`main.py:25-30`); quantity has no upper bound (`main.py:20-22`); courier inputs lack validation except name non-empty (`panels.py:13-16`, `panels.py:131-132`); menu fields lack length limits (`panels.py:19-23`). Concrete fix: add length/format checks via Pydantic constraints, cap quantity, merge duplicate item IDs or reject duplicates, and normalize email/cuisine.
9. **Authentication and wallet endpoints lack rate limiting/idempotency.** Login performs password verification with no throttling (`accounts.py:89-98`), and top-up accepts repeated positive amounts without an operation identifier (`accounts.py:106-123`). Concrete fix: add per-account/IP throttling and lockout/backoff for login; for top-up, add a client-generated operation ID or a server-side idempotency table and transactional audit records.
10. **Connections leak and the frontend keeps stale money/cart state.** `with get_db()` commits/rolls back but does not close a SQLite connection (`db.py:11-14`); e.g. `get_restaurant` continues using `conn` outside the with block (`main.py:104-115`), and serializers reuse a connection after the with block (`panels.py:81`, `panels.py:103`, `panels.py:204`). Separately, checkout does not refresh user balance after ordering (`web/src/pages/Checkout.tsx:46-49`), and cart snapshots entire menu items into localStorage (`web/src/CartContext.tsx:22-33`). Concrete fix: wrap connections in `contextlib.closing` or a FastAPI dependency that closes them; call `refreshUser()` after order success; refresh/revalidate cart menu data before checkout.

## 6. Frontend/API agreement

The React client is a routed SPA. `AuthProvider` restores a token/user from localStorage and hydrates the user via `/api/auth/me` (`web/src/AuthContext.tsx:17-39`, `web/src/AuthContext.tsx:41-66`). `CartProvider` persists a restaurant ID, menu-item snapshots, and quantities in localStorage (`web/src/CartContext.tsx:14-33`). Providers are mounted under `BrowserRouter` (`web/src/main.tsx:9-18`), and routes map home/detail/checkout/order/account/panel pages (`web/src/App.tsx:47-54`). Every API call goes through `request<T>`, which injects the Bearer token, parses errors, and returns JSON (`web/src/api.ts:3-21`).

Known disagreements and weak seams:

1. **Guest ordering:** the checkout warning says login is required (`web/src/pages/Checkout.tsx:65-68`) and disables the button when `!user` (`web/src/pages/Checkout.tsx:74`). The backend also requires a customer (`main.py:143` -> `auth.py:33-36`). There is no guest-order path; any documentation claiming otherwise is stale.
2. **Order status labels:** both customer and restaurant maps use correct Unicode keys `hazırlanıyor` and `onaylandı` (`web/src/panels/CustomerPanel.tsx:7-12`; `web/src/panels/RestaurantPanel.tsx:10-15`), but new orders store mojibake (`main.py:199`) and confirmation stores mojibake (`panels.py:237-239`). The labels fall back to raw DB strings (`web/src/panels/CustomerPanel.tsx:96`; `web/src/panels/RestaurantPanel.tsx:95`).
3. **Order detail authorization:** `OrderPage` calls the unauthenticated endpoint directly (`web/src/api.ts:49`; `web/src/pages/OrderPage.tsx:14-18`). This matches the current unsafe API but will break once the IDOR fix adds ownership checks.
4. **Balance staleness:** checkout clears the cart and navigates immediately (`web/src/pages/Checkout.tsx:46-49`) without calling `refreshUser`, so the header/checkout balance can remain stale even though the backend deducts it (`main.py:181-184`).
5. **Cart price drift:** cart lines persist the full `MenuItem` object and old delivery fee (`web/src/types.ts:78-82`; `web/src/CartContext.tsx:22-48`). If restaurant data changes, the client can display a different price/fee from the backend during order creation (`main.py:157-174`).
6. **Delivery fee source:** checkout prefers `location.state.deliveryFee`, then falls back to the first cart line (`web/src/pages/Checkout.tsx:14`). This is fragile if multiple lines exist with different snapshots or if the user arrives at checkout through another route.
7. **Silent auth failure:** failed `/api/auth/me` hydration simply clears the user (`web/src/AuthContext.tsx:35-38`), and API errors are reduced to a generic string (`web/src/api.ts:13-18`). The UI cannot distinguish invalid token, network failure, or server error.
8. **Review form errors:** the form awaits `submitReview` and then refetches with no local catch (`web/src/pages/RestaurantDetail.tsx:104-110`). A failed request bubbles to an unhandled promise rejection, leaves the form filled, and does not show an inline error.
9. **Shared submit state:** `Account.tsx` uses one `sending` state for both customer and restaurant forms (`web/src/pages/Account.tsx:12`, `web/src/pages/Account.tsx:58`, `web/src/pages/Account.tsx:75`). Submitting one form can disable or reflect the other.
