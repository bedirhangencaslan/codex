# Sepet Kod Denetimi

Bu denetim `sepet/` altındaki Python backend modulleri, `schema.sql`, frontend kaynak dosyalari, stiller, Vite/TypeScript yapilandirmalari ve README uzerinde yapildi. Derleme cikislari (`web/dist/*`), lockfile ve ikili `sepet.db` dosyasi davranis analizi icin ayri olarak degerlendirilmedi.

## 1. Module map

| Module | Responsibility | Reads | Writes |
|---|---|---|---|
| `sepet/api/db.py` | SQLite connection factory, UTC timestamp, password hashing/verification. | None directly. | None directly. |
| `sepet/api/auth.py` | Bearer token resolution and role/profile guards for customer, restaurant and courier. | `auth_token`, `user`, `restaurant`, `courier`. | None. |
| `sepet/api/accounts.py` | Registration, login, current-user lookup and customer wallet top-up. | `user`. | `user`, `restaurant`, `auth_token`. |
| `sepet/api/main.py` | FastAPI composition, restaurant browsing and customer order creation/detail. | `restaurant`, `restaurant_review`, `menu_item`, `user`, `order`, `order_item`. | `user`, `order`, `order_item`. |
| `sepet/api/panels.py` | Customer history, restaurant operations, courier assignment/delivery, delivery confirmation and earnings. | `order`, `restaurant`, `user`, `courier`, `order_item`, `menu_item`. | `order`, `courier`, `user`, `menu_item`. |
| `sepet/api/reviews.py` | Eligibility check, creation of restaurant reviews and display-rating helper. | `restaurant`, `order`, `restaurant_review`. | `restaurant_review`. |

## 5. Risks

1. **Unauthenticated customer address/phone/note disclosure.** `GET /api/orders/{order_id}` has no token or ownership dependency and returns `o.*` including address, phone, note and customer ID (`sepet/api/main.py:119-139`). Anyone who can guess or enumerate IDs can read customer delivery data. Concrete fix: require `get_current_user`, return 404 unless `order.customer_id == user.id`, or issue a short-lived signed order-access token for the confirmation page.

2. **Order status literals are double-encoded, breaking the delivery state machine.** Insert/default use `"haz\xc4\xb1rlan\xc4\xb1yor"` while panel logic compares `"haz\u0131rlan\u0131yor"` (`sepet/api/main.py:199`, `sepet/api/schema.sql:60`, `sepet/api/panels.py:174`). After a restart/reseed, restaurants cannot assign couriers because the statuses never match. Concrete fix: normalize every literal to Turkish `hazırlanıyor`, preferably via shared Python constants, migrate existing rows, and rebuild the schema default.

3. **Tokens never expire and logout does not revoke them.** Registration/login only insert a token with a creation timestamp (`sepet/api/accounts.py:50-56`); `_user_from_token()` never checks expiry (`sepet/api/auth.py:10-15`); frontend logout only deletes localStorage (`web/src/AuthContext.tsx:56-59`). Stolen tokens are effectively permanent. Concrete fix: add `expires_at`, reject expired rows, add a logout endpoint that deletes the presented token, and prune expired tokens.

4. **SQLite foreign keys are declared but never enabled.** `get_db()` opens a connection without `PRAGMA foreign_keys = ON` (`sepet/api/db.py:11-14`). SQLite therefore will not enforce most declared relationships (`sepet/api/schema.sql:10`, `23`, `29-30`, `36-37`, `55`, `62-63`, `70-72`). Concrete fix: execute the pragma immediately after connecting and include a regression test for invalid inserts.

5. **Monetary values are floating-point.** Ratings/fees/order totals/prices use `REAL` (`sepet/api/schema.sql:5-8`, `18`, `49`, `59`, `74`). `create_order()` computes and stores subtotal/total with floats (`sepet/api/main.py:166-174`) and wallet operations use float addition/subtraction (`sepet/api/accounts.py:116-119`). This invites rounding drift. Concrete fix: store minor units in integer columns, use decimal arithmetic at the boundary, and migrate existing balances/orders.

6. **Courier account creation bypasses validation used elsewhere.** Restaurant-owned courier creation checks only nonempty name and email conflict (`sepet/api/panels.py:128-145`), while normal registration validates email and minimum password length (`sepet/api/accounts.py:35-47`). This creates weak/invalid courier credentials. Concrete fix: reuse email/password validation and rate-limit this endpoint.

7. **Connections are committed but not closed.** `with sqlite3.connect(...)` commits/rolls back but does not close the connection (`sepet/api/db.py:11-14`). Every endpoint uses this pattern, e.g. `sepet/api/main.py:47`, `84`, `121`, `149`. Under sustained requests this can leak file descriptors. Concrete fix: use `contextlib.closing` around `with get_db() as conn`, or return a connection-closing context manager.

8. **Reviewer email addresses are exposed publicly.** Restaurant detail selects and returns `u.email AS user_email` without authentication (`sepet/api/main.py:94-99`, `82-83`), and the UI displays it directly (`web/src/pages/RestaurantDetail.tsx:92-97`). This leaks personal identifiers. Concrete fix: return a display name or pseudonymous ID; if email must remain available, restrict it to account owner/admin roles.

9. **Rating calculation is not review-count weighted.** The list endpoint averages the restaurant seed rating once plus one already-averaged review value (`sepet/api/main.py:49-61`), and `displayed_rating()` simply averages those values (`sepet/api/reviews.py:13-15`). One or two reviews can therefore dominate a restaurant's public score and ordering. Concrete fix: aggregate all individual review ratings and either include the seed rating once per defined prior weight or exclude it after a minimum review count.

10. **Frontend balance and totals can diverge from server state.** Checkout previews totals from localStorage cart and optional navigation state (`web/src/Checkout.tsx:14`, `20`), while the server recalculates from `restaurant` and `menu_item` (`sepet/api/main.py:150-174`). After successful order creation, the UI clears the cart and navigates away without refreshing the authenticated user (`web/src/Checkout.tsx:47-49`), leaving header/checkout balance stale until `refreshUser()` is called elsewhere (`web/src/AuthContext.tsx:61-66`). Concrete fix: return and set the new balance from order creation, or call `refreshUser()` immediately before navigation.

## 6. Frontend

The web client is a React 19/Vite SPA. `main.tsx` mounts routing and global providers (`web/src/main.tsx:9-19`). Vite proxies all relative `/api` calls to the local FastAPI backend (`web/vite.config.ts:6-10`).

`api.ts` centralizes HTTP access. Every request reads `sepet-auth` from localStorage and attaches it as a bearer token when present (`web/src/api.ts:3-12`). Non-2xx responses are converted into an `Error` using the backend `detail` string when available (`web/src/api.ts:13-19`). Endpoint wrappers cover restaurants, cuisines, orders, auth, panels, reviews and wallet top-up (`web/src/api.ts:32-123`).

Auth state is managed by `AuthProvider`: it hydrates the user from localStorage, validates it with `GET /api/auth/me`, persists login/register responses, and implements local-only logout plus server refresh (`web/src/AuthContext.tsx:25-66`). Cart state is similarly persisted to localStorage and stores a snapshot of selected menu items plus delivery fee (`web/src/CartContext.tsx:21-33`, `35-59`).

Route-to-API flow:

| UI route/component | API behavior |
|---|---|
| `Restaurants` | debounced restaurant/filter queries and cuisine list (`web/src/pages/Restaurants.tsx:24-42`). |
| `RestaurantDetail` | loads restaurant detail, submits review, and populates cart (`web/src/pages/RestaurantDetail.tsx:18-27`, `101-110`, `39-45`). |
| `Checkout` | creates an order and navigates to its unauthenticated detail page (`web/src/pages/Checkout.tsx:46-49`; `web/src/api.ts:51-67`). |
| `OrderPage` | calls `GET /api/orders/{id}` (`web/src/pages/OrderPage.tsx:14-19`; `web/src/api.ts:49`). |
| `Panel` | routes role to customer, restaurant or courier panel (`web/src/pages/Panel.tsx:30-32`). |
| `CustomerPanel` | history, wallet top-up and delivery confirmation (`web/src/panels/CustomerPanel.tsx:23-49`). |
| `RestaurantPanel` | orders/menu/couriers/earnings plus courier and menu creation (`web/src/panels/RestaurantPanel.tsx:25-46`, `132-173`). |
| `CourierPanel` | assigned orders and delivery action (`web/src/panels/CourierPanel.tsx:10-23`). |

Main frontend/backend disagreements:

- The frontend assumes the order detail page can be opened after creation, but does not pass or verify an ownership contract (`web/src/pages/OrderPage.tsx:14-19`), while the backend currently enforces neither auth nor ownership (`sepet/api/main.py:119-139`).
- Frontend status labels expect correct Turkish literals (`web/src/panels/CustomerPanel.tsx:7-12`; `web/src/panels/RestaurantPanel.tsx:10-15`), but backend order creation/schema seed use double-encoded text (`sepet/api/main.py:199`; `sepet/api/schema.sql:60`). This breaks the assignment UI and displays the raw corrupt status.
- Frontend cart prices/delivery fee are snapshots (`web/src/CartContext.tsx:35-47`; `web/src/Checkout.tsx:14`, `20`), while backend recomputes them from current database rows (`sepet/api/main.py:156-174`). The displayed total can differ from the charged total.
- Frontend balances are local React state (`web/src/AuthContext.tsx:41-66`), but order creation does not refresh them (`web/src/Checkout.tsx:47-49`), so wallet display lags server state.
- There is no logout API call because no such endpoint exists; frontend logout is purely client-side (`web/src/AuthContext.tsx:56-59`; `sepet/api/accounts.py:59-123`).
