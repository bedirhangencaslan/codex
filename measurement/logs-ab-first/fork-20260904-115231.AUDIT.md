## 5. Risks

1. **Order detail is fully public and leaks customer PII.** `GET /api/orders/{order_id}` has no dependency and returns every order column, including `address`, `phone`, and `note`, then also returns items (`sepet/api/main.py:119`, `sepet/api/main.py:137`). The frontend's order detail calls this endpoint directly (`sepet/web/src/pages/OrderPage.tsx:15`, `sepet/web/src/pages/OrderPage.tsx:37`). Concrete change: require authentication, restrict customers to `order.customer_id`, restaurants through ownership, and couriers through `courier_id`; for restaurant/courier users return only fields needed for delivery.
2. **The order state machine is split across incompatible Unicode literals.** The schema default and `main.py` create `hazÃ„Â±rlanÃ„Â±yor`, while `panels.py` checks the correct `hazÄ±rlanÄ±yor` (`sepet/api/schema.sql:60`, `sepet/api/main.py:199`, `sepet/api/panels.py:174`). A public order can therefore be created but never assigned a courier. The same class of mismatch appears in `main.py`'s review eligibility query (`sepet/api/main.py:109`) versus the correct query in `reviews.py` (`sepet/api/reviews.py:34`). Concrete change: define one `OrderStatus` enum and one constant set; write values from those constants, and add a migration that normalizes existing rows and a schema `CHECK` constraint.
3. **Foreign-key enforcement is off.** Every SQLite connection is opened without `PRAGMA foreign_keys = ON` (`sepet/api/db.py:11`). Even though references are declared in `sepet/api/schema.sql:10`, `:23`, `:29`, `:30`, `:36`, `:37`, `:55`, `:62`, `:63`, `:71`, `:72`, orphan rows can be inserted by raw SQL or future code paths. Concrete change: execute `PRAGMA foreign_keys = ON` immediately after every connection is opened.
4. **Money uses binary floats.** `restaurant.rating`, `delivery_fee`, `min_order`, `user.balance`, `menu_item.price`, `order.total`, and `order_item.unit_price` are `REAL` (`sepet/api/schema.sql:5`, `:6`, `:7`, `:18`, `:49`, `:59`, `:74`). Totals and balances are also rounded in float arithmetic (`sepet/api/main.py:166`, `sepet/api/main.py:174`, `sepet/api/accounts.py:114`). This is incorrect for currency and can drift after repeated operations. Concrete change: store minor units as INTEGER and use Decimal only at API boundaries, with two-column numerator/denominator precision explicitly documented if a fractional unit is required.
5. **Tokens are perpetual and logout is client-only.** `issue_token` inserts a token with only `created_at` (`sepet/api/accounts.py:50`), while authentication validates it without an expiry or revocation check (`sepet/api/auth.py:10`). `logout()` only deletes the browser value (`sepet/web/src/AuthContext.tsx:56`). Concrete change: add `expires_at` and `revoked_at`, reject expired/revoked tokens, provide a logout endpoint, rotate tokens periodically, and avoid returning user data to be persisted in localStorage.
6. **Bearer tokens in localStorage expand the blast radius of any XSS.** The token is read from `localStorage` and placed in every request header (`sepet/web/src/api.ts:4`, `sepet/web/src/api.ts:9`), and login/register persist it there (`sepet/web/src/AuthContext.tsx:41`). Combined with non-expiring tokens, script execution becomes account takeover. Concrete change: move auth to an HttpOnly, Secure, SameSite cookie with CSRF protection, or at minimum use short-lived in-memory tokens and revocable refresh tokens.
7. **Server-side order input validation is missing.** `OrderInput` only types address, phone, and note as strings (`sepet/api/main.py:25`). The API accepts whitespace-only address/note and arbitrary phone text because backend validation is absent; the stricter checks only live in the frontend (`sepet/web/src/pages/Checkout.tsx:35`, `sepet/web/src/pages/Checkout.tsx:40`). Concrete change: constrain non-empty trimmed address, normalize phone using a pattern or digit count, bound note/item quantities, and reject duplicate `menu_item_id` lines or consolidate them server-side.
8. **Duplicate registration can become an unhandled 500.** Registration checks then inserts without relying on the unique constraint for error conversion (`sepet/api/accounts.py:63`, `sepet/api/accounts.py:65`); the schema declares email uniqueness (`sepet/api/schema.sql:15`). A concurrent request can pass the check and cause SQLite's `IntegrityError` to surface as an internal error. Concrete change: catch `sqlite3.IntegrityError` on insert and return the existing 409 response.
9. **Courier creation accepts unsafe credentials.** `CourierInput` has no password length constraint and does not trim/validate name or email (`sepet/api/panels.py:13`). The handler hashes whatever password arrives (`sepet/api/panels.py:138`). Concrete change: reuse shared email/password validation, enforce a minimum password length and non-empty name, and report duplicate email as 409 rather than relying on the unhandled unique failure.
10. **The customer's visible balance is not refreshed after an order.** Checkout uses `user.balance` from React state (`sepet/web/src/pages/Checkout.tsx:21`, `sepet/web/src/pages/Checkout.tsx:89`), but successful `createOrder` neither refreshes the user nor clears the cart until after a new order response (`sepet/web/src/pages/Checkout.tsx:47`). `create_order` does deduct the balance (`sepet/api/main.py:181`), so the next checkout can show stale funds. Concrete change: refresh `/api/auth/me` immediately after order creation before navigation, or return the new balance from `POST /api/orders` and update AuthContext.

Two secondary risks worth scheduling after the top ten: `serialize_orders` performs an `order_item` query per order (`sepet/api/panels.py:39`), producing N+1 behavior; and no order list is paginated (`sepet/api/panels.py:71`, `sepet/api/panels.py:102`, `sepet/api/panels.py:194`).

## 6. Frontend

### API Access

`web/src/api.ts` centralizes calls in `request<T>()`. It reads a token from the `sepet-auth` localStorage record, adds `Authorization: Bearer ...`, adds JSON headers only when a body exists, parses FastAPI error `detail`, and throws a generic fallback message (`sepet/web/src/api.ts:3`, `sepet/web/src/api.ts:8`, `sepet/web/src/api.ts:13`). During development, Vite proxies `/api` to `http://127.0.0.1:8000` (`sepet/web/vite.config.ts:6`). Routes are mounted from `main.tsx` with auth and cart providers (`sepet/web/src/main.tsx:11`), and application routes are defined in `App.tsx` (`sepet/web/src/App.tsx:47`).

State flow:

- `AuthProvider` restores a user from localStorage, validates it through `/api/auth/me`, persists login/register responses, exposes refresh, and performs only local logout (`sepet/web/src/AuthContext.tsx:25`, `:41`, `:46`, `:56`, `:61`).
- `CartProvider` stores a single-restaurant cart and its lines in localStorage, computes subtotal client-side, and clears when the last line is removed (`sepet/web/src/CartContext.tsx:21`, `:35`, `:50`, `:61`).
- Restaurants and filters call `GET /api/cuisines` and `GET /api/restaurants` (`sepet/web/src/pages/Restaurants.tsx:24`, `:33`; API paths at `sepet/web/src/api.ts:32`, `:47`).
- Restaurant detail fetches one restaurant, adds cart lines, and posts reviews (`sepet/web/src/pages/RestaurantDetail.tsx:20`, `:83`, `:106`; `sepet/web/src/api.ts:44`, `:110`).
- Checkout creates an order, clears the cart, and navigates to `/order/:id` (`sepet/web/src/pages/Checkout.tsx:47`).
- Role panels call history/restaurant/courier APIs and then reload their data after actions (`sepet/web/src/panels/CustomerPanel.tsx:23`, `:33`, `:38`; `RestaurantPanel.tsx:25`, `:42`; `CourierPanel.tsx:10`, `:20`).

### Disagreements And Gaps

1. **Status labels do not match persisted mojibake.** Frontend maps the correct strings `hazÄ±rlanÄ±yor`, `kuryede`, `teslim_edildi`, `onaylandÄ±` (`sepet/web/src/panels/CustomerPanel.tsx:7`, `sepet/web/src/panels/RestaurantPanel.tsx:10`), but orders written by `main.py`/`schema.sql` use the double-encoded creation status. Restaurant assignment and UI status handling diverge from the written state.
2. **The order page implies live progress but never polls.** It states the status updates when a courier is assigned (`sepet/web/src/pages/OrderPage.tsx:51`), yet it fetches only once on mount (`sepet/web/src/pages/OrderPage.tsx:14`). Concrete change: either remove that claim or poll/subscribe and refresh.
3. **Balance is stale after orders.** The backend deducts `order.total` from the customer (`sepet/api/main.py:181`), but `Checkout` neither updates AuthContext from a returned balance nor calls `refreshUser` (`sepet/web/src/pages/Checkout.tsx:47`). Wallet top-up does refresh (`sepet/web/src/panels/CustomerPanel.tsx:43`).
4. **Frontend validation is not a security boundary.** Phone and address rules exist only in `Checkout` (`sepet/web/src/pages/Checkout.tsx:36`), while backend models accept unconstrained strings (`sepet/api/main.py:25`).
5. **Panel mutation errors are not surfaced.** `RestaurantPanel.assign`, menu creation, and courier creation throw without local error handling (`sepet/web/src/panels/RestaurantPanel.tsx:42`, `:134`, `:159`); likewise `CourierPanel.deliver` (`sepet/web/src/panels/CourierPanel.tsx:20`) and review submission (`sepet/web/src/pages/RestaurantDetail.tsx:104`). The generic request wrapper throws, but these callers leave the UI without a visible state change.
6. **Race conditions in list fetches are unguarded.** `Restaurants` debounces timer setup but does not cancel or ignore stale in-flight responses (`sepet/web/src/pages/Restaurants.tsx:30`). A slower earlier response can overwrite a newer filter's result.
7. **Auth logout is frontend-only.** The server token remains valid after `logout()` (`sepet/web/src/AuthContext.tsx:56`) because no invalidation endpoint exists.
